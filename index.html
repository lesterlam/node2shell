1 · The trigger

why draining a 2²⁴ counter needed a zero-cost command

The bug fires when a block-length counter reaches 0 while the meta-block declared only one block type. BrotliDecoderStateMetablockBegin() resets every counter to 2²⁴ at the start of each meta-block, so the drain has to happen inside one meta-block — and a negative meta_block_remaining_len is rejected by WriteRingBuffer, so the drain may not cost anything. A static-dictionary copy whose transform returns 0 does exactly that: BrotliTransformDictionaryWord() returns idx (bytes written), not the transformed length, and transform 34 (OMIT_FIRST_4, empty affixes) returns 0. 

/* per command: insert 0, copy 4, explicit distance */
pos += len;                          /* +0  */
s->meta_block_remaining_len -= len;   /* -0  */
--s->block_length[1];                 /* the counter we are draining */
--s->block_length[2];                 /* ...and the distance counter too  */

2 · Where the write actually lands

the write index is the buffer_length field — but the ceiling is not

An attacker byte at index i lands at decoder-state offset 72 + i. BROTLI_FAST_INPUT_SLACK = 28 means both fill loops only run while fewer than 28 input bytes remain, so at most 27 bytes are ever written. Drag the slider — this is the measured behaviour, not a sketch.
